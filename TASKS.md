# local-agent: task list

Tasks that carry out [PLAN.md](PLAN.md). They run one at a time, in order. Each task goes implementer → reviewer → (fix loop) → human approval before the next one starts.

Rules for every task:
- Keep the existing CLI working at the end of each task.
- Add or update pytest tests for new behaviour. `uv run pytest` must pass.
- Update README.md when user-visible behaviour or setup changes.
- Resolve any **verify** item the task owns and record the finding in the task's notes below.
- Stay inside the task's scope; note follow-ups instead of doing them.

Status: `todo` · `in progress` · `in review` · `done`

**T02**
- **ACP decision: align, do not adopt yet.** The Agent Client Protocol (agentclientprotocol.com) is built for editor-to-agent frontends, which is the T11/T19 case, so its shapes are a good target. We keep our own internal events (names from PLAN.md §1) and use ACP names and values where they exist: tool kinds (`read`, `edit`, `execute`, `fetch`, ...), tool call statuses, permission option kinds (`allow_once`, `reject_once`), stop reasons (`end_turn`, `max_turn_requests`, `cancelled`) and `toolCallId`. T11 maps our events 1:1 to `session/update` (`text_delta` to `agent_message_chunk`, `tool_call`/`tool_result` to `tool_call`/`tool_call_update`, `approval_request` to `session/request_permission`, `turn_done` to the `session/prompt` response). We do not build a stdio server here (T11).
- ACP gaps to handle at T11, not now: `tool_call` requires a `title` (our `ToolCall` has none yet); ACP's `tool_call` status values `pending` and `in_progress` are not emitted (we send only final results); `text_delta` needs a `messageId` for chunks. The ACP overview page does not name the discriminator values, so T11 must check the schema reference, not only the protocol pages.
- Verified against the spec (fetched 2026-11-23): `sessionUpdate` values `tool_call`/`tool_call_update`/`agent_message_chunk`; ToolCallStatus `pending`/`in_progress`/`completed`/`failed`; ToolKind includes `switch_mode`; PermissionOptionKind `allow_once`/`allow_always`/`reject_once`/`reject_always`; StopReason `end_turn`/`max_tokens`/`max_turn_requests`/`refusal`/`cancelled`.
- Design: `core/events.py` holds the event dataclasses (each with a wire `type` tag, so T11 can serialise them). `permissions.py` holds `Risk`, `needs_approval` (only `read` is auto-allowed), the `Approver` protocol and `DenyAll` (the default when no approver is passed, so risky tools are refused). `tools/registry.py` holds `@tool(risk=, location=, denied_message=, approval_title=, preview=, registry=)`, the `Tool` object (`schema()`, `call()`, `approval_request()`) and the JSON schema builder. `core/loop.py` `run_turn(messages, client, *, emit, approver)` emits events and never prints.
- The event order for a turn with a write is `tool_call`, `approval_request`, `tool_result`, then `text_delta` and `turn_done`. The core emits `approval_request` to the sink (so the frontend can show the preview) and then calls `approver.decide()`. The CLI renders the preview from the sink and asks y/n from the approver.
- Schemas: the three builtins produce the same `tools=` entries as ollama's own function conversion before T02 (checked by script and pinned in `tests/test_registry.py`), including `"description": ""` on parameters without a description.
- `core/__init__.py` no longer re-exports `loop`, to avoid an import cycle (`core` -> `loop` -> `tools` -> `core.events`). Import `local_agent.core.loop` directly.
- Terminal output is unchanged except that tool results are not printed (as before) and the max-rounds message is now rendered by the CLI from `turn_done`. Verified by a piped smoke test against `qwen3-vl:8b`: `read .python-version` returned `3.14`, and a write asked for approval, showed the preview and wrote the file after `y`.
- Behaviour kept on purpose: `text_delta` is emitted only for the final reply (intermediate text next to tool calls is still not shown, as before). Denied tools return the old messages ("User denied file write." and "User denied command execution.") to the model.
- Follow-ups: T03 streams `text_delta` and adds `cancelled`. T07 adds `ALLOW_ALWAYS` and diff previews. T11 adds `title` and `messageId` as above. Client-located tools (`Location.CLIENT`) are registered but the core refuses to run them with a clear error until T20 adds a client runner. `tool_name` in tool messages is still missing (T03). The approval `risk` field is a string on the event (`"write"`), so events stay free of imports from tools.
- Review fixes: arguments are bound against the tool's signature before the approval request is built, so bad arguments to a risky tool return the usual "Error calling <tool> ..." text (naming the real tool) and the user is not asked. An approver that raises counts as a refusal, and the tool does not run. `Decision.allowed` is the one way the loop checks a decision.
- Follow-up (before T06): Google-style `Args:` docstring blocks are not parsed into per-parameter descriptions. Only `Annotated[..., "desc"]` sets them. Revisit when the read tools with many parameters are added.
- Follow-up (T20): `Tool.fn` is mandatory, so client-located tools need a stub body. Consider making `fn` optional for `location=CLIENT`.
- Follow-up (hardening): argument types are not validated against the schema (only the signature is bound). A model that sends `"5"` for an `int` reaches the tool unchanged. Add type coercion or validation.

**T03**
- **Streaming:** `run_turn` calls the client with `stream=True` and emits `text_delta` per chunk. Content and `tool_calls` are collected across all chunks (`core/loop.py` `_stream_reply`) and appended to history as an `ollama.Message` only when the stream has finished. The CLI prints one `Agent: ` line and appends the deltas to it (`Renderer` in `frontends/cli.py`).
- **Behaviour change:** text that comes before tool calls in a round is now streamed and shown (it used to be dropped). The core cannot know a reply has tool calls until the stream ends, so it streams everything. The T02 note about final-reply-only text no longer holds.
- **Cancel:** `run_turn(..., cancel=threading.Event)` is checked between chunks, before each round and before each tool call. Ctrl+C arrives as `KeyboardInterrupt`; the core catches it at the streaming, tool and approval steps (and once more around the whole turn) and treats it as a cancel. The turn ends with `turn_done` (`stop_reason="cancelled"`). The CLI shows `[Turn cancelled]` and returns to `You:`. Ctrl+C at the prompt exits.
- **History invariant (chosen: synthetic results + drop partial reply):** every tool call in an assistant message gets a tool message. Calls that did not run get `"Cancelled by user."` as a failed `tool_result`, and the event stream shows a `tool_call` and a `tool_result` for each. A reply cut off mid-stream is not appended, so its partial tool calls never reach history. `tests/test_streaming.py` asserts the invariant with `assert_tool_calls_answered` after every cancel and error case.
- **Errors:** an `error` event is emitted and the turn ends with no `turn_done` (matches ACP, where a failed prompt is a JSON-RPC error). Mapping: `ConnectionError` and `httpx.ConnectError` give "Cannot reach Ollama at <host>. Start it with `ollama serve` ..."; `ResponseError` 404, or "not found" in its text, gives "Model '<model>' is not installed ... `ollama pull <model>`"; other `ResponseError`s and `httpx.TransportError`s are shown with their text. Other exceptions still propagate (they are bugs).
- **Verified against the client (ollama 0.6.x, httpx 0.28):** with `stream=True` the client returns a generator. A refused connection surfaces when the stream is first read, as a raw `httpx.ConnectError`, not as `ConnectionError` (that is only raised on the non-streaming path). A missing model is `ResponseError` 404 before the stream starts. `Message` has `tool_name`, which is now set on every tool message.
- **Verified live (qwen3-vl:8b):** a piped turn streams and reads `.python-version` (`3.14`). With `OLLAMA_HOST=http://127.0.0.1:1` the CLI prints the Ollama-down error, stays at the prompt, and exits 0. Model not found (`no-such-model:0b`) gives the `ollama pull` message. A cancel from another thread after 8 s on a real stream returns `cancelled` with history `[system, user]`.
- **Not verified:** a real Ctrl+C in a console. Tests inject `KeyboardInterrupt` at each step instead. UNVERIFIED, needs a manual check: a real Ctrl+C on Windows during a silent stream (model load or prompt eval, when no chunk arrives) may not interrupt until the next chunk. Fix options: an httpx read timeout via `ollama.Client(timeout=...)`, or a worker thread (T11/T16).
- **Follow-up (before T11/T16):** on Windows, a blocking socket read may not be interrupted by Ctrl+C until the next chunk arrives, and the ollama client has no read timeout by default. If real Ctrl+C feels slow, run the turn on a worker thread or add a read timeout. Check it by hand first.
- **Deferred to T04/T16:** `thinking` passthrough or a "thinking..." indicator. qwen3-vl thinks before answering and the `thinking` field is ignored, so the user sees nothing for a while. **Resolved in T04** (see T04 notes).
- **Deferred to T04:** after a cancel or an Error with no reply, the user's message stays in history, so a retry adds a second user message. Decide whether to remove it on failure. **Resolved in T04** (removed in the REPL).
- **Follow-up:** `_host_of` reads the host from the ollama client's httpx base URL; fakes fall back to `OLLAMA_HOST`. **Resolved in T04:** the host comes from `Settings` and is passed explicitly.

**T06**
- **read_file:** optional `start_line` and `end_line` (1-based, inclusive, `Annotated` descriptions). Without them the output is the whole file, as before. With them it is numbered (`12: text`) under a header `[lines 3-5 of 10]`. A range past the end, `start_line` past the end, or `end_line < start_line` is a clean error text; `end_line` past the end is clipped.
- **Optional paths:** `list_dir`, `glob`, `grep` and `git_diff` take an optional `path`. Omitted means the workspace (the tool uses `context.workspace`). A `null` value is now treated the same as omitted: `sandbox.check_arguments` skips it, so the tool gets `None`. Before, `null` was refused as "a path must be text". Optional path parameters may be typed `str | None`; the `@tool` check accepts that (`registry._is_path_type`).
- **Output cap:** `truncate()` moved to `tools/output.py` and is shared by `read_file`, `run_command` and the new tools. Marker unchanged: `...[truncated N chars]`. The item caps add their own line: `[stopped at N ...]` (glob, grep), `[... N more entries not shown]` (list_dir).
- **Search scope:** `glob` and `grep` drop any match whose resolved path is outside the folder they start from (junctions and symlinks followed, via `sandbox.resolve`), and skip `.git`. The base folder itself is already sandboxed (and approved if outside). So an approved outside folder is searched in full, but the search never follows a link out of it. `glob` also rejects patterns with `..`, a drive, a colon or a leading slash.
- **grep:** pure Python, `re` syntax, `ignore_case` and `include` (file-name glob) options. Binary files (NUL in the first 8 KB), files over 2 MB and `.git` are skipped. Lines are cut to 300 characters. Output is `path:line: text`, with the path relative to the workspace when inside it, else absolute.
- **git tools:** `git --no-pager -c color.ui=never` in the workspace, no shell, 30 s timeout, `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0` (status does not take index locks). Missing git, a non-repository workspace and other failures come back as text. `git_diff` has `path` (sandboxed, passed after `--`) and `staged`. `git_log` has `max_count` (default 20, 1 to 200). Untracked files do not appear in `git_diff`.
- **Repo config cannot run commands (review fix):** every git call also passes `-c core.fsmonitor=false`, `-c core.untrackedCache=false` and `-c core.hooksPath=<nul>`, and `git_diff` adds `--no-textconv`. A `.git/config` `core.fsmonitor` or a `.gitattributes` textconv driver used to run its command from `git_status` or `git_diff` (verified: the marker file was created before the fix). Tests: `test_git_status_and_diff_do_not_run_fsmonitor_from_the_repo_config`, `test_git_diff_does_not_run_a_textconv_from_the_repo_config`.
- **No parent repository (review fix):** `GIT_CEILING_DIRECTORIES` is set to the workspace's parent, so git does not climb above the workspace. A workspace that is a repo root works as before.
  - **Known limitation / follow-up:** a workspace that is a subfolder of a bigger repo now reports "not a git repository". Before, it showed the parent repo's status and diff. Supporting that needs a deliberate design (for example showing paths relative to the repo root).
- **Filter override (fix rounds 2 and 3):** before each git call, the repo-scope `filter.<name>.clean|smudge|process` keys (local or worktree scope, including include.path) are listed with `git config -z --show-scope` and blanked, so git_status and git_diff run no repo-defined filter drivers. The overrides go in through the environment (`GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_n`, `GIT_CONFIG_VALUE_n`), not `-c`: `-c key=` splits at the first `=`, so a filter named `a=b` (`*.txt filter=a=b`) still ran its clean filter (verified: plain `git diff` fired it, and so did the `-c` form). Env entries are appended after any already inherited, and they are command scope, so they beat local config. Each filter name also gets `filter.<name>.required=false`, so a repo with `git lfs install --local` does not fail with "clean filter 'lfs' failed". System and global filters such as Git LFS are untouched. **Fail closed:** if the listing times out, raises OSError, or exits with a code other than 0 (keys found) or 1 (none found), git is not run and the tool returns "Error: could not read the git config, so git was not run ...". A non-repository workspace still gets "The workspace is not a git repository". Tests: `test_git_tools_do_not_run_a_*_filter*`, `test_git_diff_keeps_entries_already_in_the_environment_and_still_blocks_the_filter`, `test_a_local_required_filter_does_not_make_the_diff_fail` and `test_git_does_not_run_when_the_filter_listing_fails` in `tests/test_read_tools.py`.
- **Not set: `GIT_CONFIG_NOSYSTEM=1`.** Git for Windows sets `core.autocrlf=true` in the system config. Ignoring the system config made every CRLF checkout show as modified (checked with a scratch repo). Repo-controlled settings are covered by the `-c` flags above, and the system config is not repo-controlled, so it is kept.
- **read_file line numbers (review fix):** the ranged branch splits on `\n` only (a trailing `\r` is dropped per line), not `str.splitlines()`, so \x0b, \x0c, \x1c-\x1e, \x85, \u2028 and \u2029 stay inside a line. A trailing newline does not add an empty line to the total. The whole-file output is unchanged. Test: `test_read_file_ranged_lines_split_only_on_newline`.
- **Follow-ups:**
  - Argument types are still not validated (T02 hardening note). A model that sends `"5"` for `start_line` gets a TypeError text from the loop, not a range error.
  - `glob` and `grep` can still walk into a junction that leads outside before the result is dropped. This costs time, but the walk never returns a path outside the base.
  - `grep` reads each file in full (up to 2 MB). Fine for a workspace; a streaming reader would be needed for very large searches.

**T07**
- **Session approvals (design):** `a` ("allow always for this session") is offered only for a call that may be allowed for the session: a tool's own question, not an outside-workspace one. `SessionApprovals` (permissions.py) keys it by (tool name, workspace folder), so a new REPL session starts empty. A tool sets `allow_always=`: `True` (default), `False` (never offered, never remembered, used for `git_commit`), or a hook (like `precheck`) that decides per call. `sandbox.session_allowance_ok` is the hook for `write_file` and `edit_file`: a path with any component named `.git` (any case) asks every time and offers no `a`. The outside-workspace question is still asked for every path, and it never offers `a`. An `a` to a request that does not offer it counts as `allow_once`. Tests: `tests/test_session_approvals.py`.
- **Approval answers:** `Tool.approval_request` builds `options` from `session_allowed_for`, so `ApprovalRequest.options` says whether `allow_always` is offered. `_ask` refuses anything that is not a string or not a known `Decision`; `None`, `True` and `1` are refused (they already were, by `Decision(...)` raising; the test now pins it).
- **`edit_file` (edit_tools.py):** exactly one occurrence of `old_text` is replaced. Zero matches, several matches (overlapping ones included: `aa` in `aaa` is two matches), an empty `old_text` and `old_text == new_text` are errors, checked in the precheck before the question. The error names each matching line once. Line endings: a file whose every line ends in CRLF is matched with LF and written back with CRLF; a file with no CRLF is matched as written; a mixed file is matched exactly as it is and nothing is rewritten. The file is written as bytes, so nothing else changes. A BOM stays in front of the first line; `old_text` at the start of the file matches without it, and a BOM inside `old_text` also matches (checked). Only UTF-8 text is edited (NUL bytes or invalid UTF-8 are refused). The diff marks a last line without a newline with `\ No newline at end of file` instead of adding one.
- **`write_file` preview:** a diff when the file exists and is UTF-8 text (`\n` becomes `os.linesep`, so the preview matches what Windows writes); otherwise the proposed content.
- **`git_commit` (git_write.py):** no repository code runs. `git add` and `git commit` use `read_tools.hardened_git` (the same helper as the read tools: `core.fsmonitor=false`, `core.untrackedCache=false`, `core.hooksPath` to the null device, `GIT_CEILING_DIRECTORIES`, the repo-scope filter override through `GIT_CONFIG_COUNT`, failing closed, and `GIT_TERMINAL_PROMPT=0`). The commit also gets `--no-verify` and `-c commit.gpgsign=false`, so no pre-commit hook, clean filter or gpg program runs. Verified by tests: a pre-commit hook, `core.fsmonitor`, a clean filter and a `gpg.program` set to a marker command all leave their marker files absent. Commits are never remembered for the session. With paths it stages them and commits with `--only`. If the commit fails after the `git add`, the paths stay staged and the error says so.
- **Repo filters (decided, tested):** with `paths`, a path whose `filter` attribute names a repo-defined filter (`filter.<name>.clean|smudge|process` in local or worktree config) is refused in the precheck, before the question: "These paths use a repo-defined filter (<name>): <paths>. Stage them yourself with `git add`, then call git_commit without paths." A folder, a wildcard or a backslash path is refused too while the repo defines any filter, since it can reach a filtered file. A filter defined only in the global or system config does not refuse. The check reads `git check-attr` and the config listing through `hardened_git`, and fails closed if either cannot be read. Without paths nothing changes: the staged blob (for example `POINTER:13`) is what is committed. Tests in `test_git_write.py`: the refusal (the approver is never asked, no commit), the no-paths commit of the filtered blob, an uncovered path still committing, and the global-only filter.
- **Commit trade-off:** with paths, a repo-defined filter is refused rather than run or skipped (see above). A repo's pre-commit hook or gpg program does not run. The preview says so (`HOOKS_NOTE`). Git still reads the system and global config, which the repo cannot set.
- **Timeouts (process.py):** `run_command`, `run_tests` and the git commit path run through `run_process`, which starts the child in its own process group (`CREATE_NEW_PROCESS_GROUP` on Windows, a new session elsewhere). On a timeout or Ctrl+C it ends the tree (`taskkill /T /F /PID`, then `proc.kill()`; `killpg` elsewhere), then reads the output for at most 5 s. Measured: `ping -n 15 127.0.0.1` with a 3 s limit returned in 3.5 s, where a plain `subprocess.run` took 14.3 s. Test: `test_a_timeout_kills_the_children_too_so_the_call_returns_in_time`.
- **Default shell is cmd (decision):** `run_command` runs cmd unless `shell` is `powershell`, so the behaviour of T06 and earlier is kept. The T07 change to PowerShell is reverted. The schema describes `cmd (the default)`. `run_command` now runs `cmd /d /c`, so AutoRun registry commands are skipped.
- **`run_tests`:** runs the resolved command through cmd. Order: the `command` argument, then `test_command` from the config (a non-empty command line, validated in config.py), then `uv run pytest -q` (pyproject.toml) or `npm test` (package.json). Nothing resolves: the call is refused before the question.
- **`run_command` and tests are not path-sandboxed:** they always ask (exec tier) and start in the workspace. Same as before.
- **Preview and option fields:** `Preview.shell` names the shell for a command preview (`PowerShell` or `cmd`). `ApprovalRequest.options` lists the answers offered (`allow_once`, `allow_always`, `reject_once`). The registry gained the `precheck` hook (runs before the question) and `allow_always`. `sandbox.check_arguments` resolves each item of a list-of-paths argument (`list[str]`), and an absent or null optional path is not resolved.
- **Tests:** `test_edit_tools.py`, `test_exec_tools.py`, `test_git_write.py`, `test_session_approvals.py`, and the changed `test_approval.py`, `test_registry.py`, `test_sandbox.py`, `test_tool_context.py`.

Non-ASCII output from Windows PowerShell 5.1 is not verified. A real gpg or Git LFS setup is not verified (the tests use a marker command). **T09**
- **SDK (verified from the installed source):** `uv add mcp` gave `mcp` 2.3.0 (with `mcp-types` 2.3.0), installed and imported on Python 3.14.10. This is the v2 API: `FastMCP` is now `mcp.server.mcpserver.MCPServer`, and `mcp.server.fastmcp` raises on import. The client used is `mcp.Client(stdio_client(params, errlog=...))`, which runs `ClientSession` underneath. `list_tools(cursor=)` returns `ListToolsResult` (`tools`, `next_cursor`), and `call_tool(name, args)` returns `CallToolResult` (`content`, `is_error`, `structured_content`). Tool errors come back as `is_error` results. An unknown tool is also an `is_error` result. A server that dies mid-call makes `call_tool` raise `MCPError("Connection closed")`. The client's default mode is `auto` (it probes `server/discover`, then falls back to `initialize`); the echo test server negotiated `2026-07-28`.
- **Runtime (`mcp_hub.py`):** one daemon thread with its own asyncio loop. Each server runs as one task: the SDK needs the client entered and left in the same task. Sync calls use `asyncio.run_coroutine_threadsafe` and poll every 0.1 s, so Ctrl+C, a cancel event and the time limit are seen at once. Starts run in parallel. A server that does not answer within `command_timeout_s` is cancelled and reported. Server stderr goes to a temp file per server, and only a start failure shows its last 500 characters. `close()` ends each server (the SDK closes stdin, waits up to 2 s, then kills the process tree) and removes its tools from the registry.

Unknown keys, wrong types, bad risk names, bad server names and a missing command raise `ConfigError` naming the setting. Server names are letters, digits and hyphens only (no underscore, so `__` cleanly separates server and tool). Stdio only; HTTP transports are a follow-up.
- **Names:** `<server>__<tool>`. Characters outside `[A-Za-z0-9_-]` become `_`, the name is cut to 64 characters (a common limit for function names), and a name already in the registry is skipped with a warning. A server that exits gives `Error: <tool> did not complete: the server failed (...)`, and the agent keeps running.

**T10**
- **Sources and order (decided):** built-in tools (registered on import), then the `*.py` files directly in the plugin folder (name order), then entry points in group `local_agent.tools` (name order), then MCP servers. `cli.run` calls `tools/plugins.py` `load_plugins` before MCP starts, and `PluginRuntime.close()` removes the plugin tools at exit, as for MCP.
- **Plugin folder:** `plugin_dir` in the config, default `<config folder>\tools` (`config.default_plugin_dir`). Not created by the app; a missing folder means no plugins and no warning. Not recursive; names starting with `_` are skipped.
- **File plugins:** run as module `local_agent_plugins.<stem>`. The source is compiled and executed directly, so no `.pyc` is written into the user's folder and an edited file is always the one that runs.
- **Entry point rule (decided):** the value must name a module; importing it registers its tools. `module:attr` is refused before anything is imported, with a warning (a function could be a tool itself). A module already imported by other code in the process is not run again, so it registers nothing; the loader warns when a plugin registers no tools.
- **Refusal has no side effects (S1, found by the review and fixed):** the first version imported `module:attr` before refusing it. The rollback removed its tools but left the module in `sys.modules`, so a second valid entry point on the same module loaded "0 tools" silently. Now the check comes first. Test: two entry points on one module, the attr form refused and the module form loads.
- **Reloading in one process (S2, found by the review and fixed):** the modules the loader imports (plugin modules, `local_agent_plugins.` helpers, and the new modules of an entry point's top-level package) are recorded. `close()` and a rollback remove them from `sys.modules`, so a later load runs them again. Before, load, close, load gave "0 tools" with no warning.
- **Zero tools:** a plugin that loads with no tools gets `Warning: plugin 'x' registered no tools.` and is left out of the `[plugins] loaded` line.
- **Helper files (S3):** a file starting with `_` is not a plugin, but a plugin can `from . import _helper`. Each file-plugin load installs a stub package `local_agent_plugins` (`__path__` = the plugin folder), replacing any stale one, so two folders in one process do not share helpers. `sys.dont_write_bytecode` is set while file plugins load, so helpers write no `__pycache__` into the user's folder. `close()` removes the stub. The README documents the rule.
- **Disabled names (N1):** `disabled_plugins` matches case-insensitively (casefold). One name is checked against both file stems and entry point names; the README says so.
- **Ctrl+C and cleanup (N2):** `cli.run` loads plugins inside its try. A KeyboardInterrupt during plugin import or MCP start returns without a traceback. `load_plugins` closes what it loaded before re-raising, and the `finally` closes plugins and MCP even if `start_mcp_servers` raises.
- **All or nothing per plugin:** any exception (syntax error, import error, invalid tool, or a raise after some `@tool`s) removes the tools that plugin added (registry key diff) and prints one warning. A name collision does not fail the plugin: `registry.skip_name_collisions()` makes a `@tool` whose name is taken skip it and report it, so the plugin's other tools still load. Outside plugin loading the registry still raises `ValueError` on a duplicate.
- **Risk (decided):** `@tool` already has no default for `risk` (it is a required keyword), so a plugin tool without one fails to load with a warning. No default to `exec` or `read`: an omitted tier would be a guess.
- **Profiles, approvals, sandbox:** unchanged, because plugin tools go through the same loop. A plugin's `paths=("path",)` gets the same workspace check (tested with an outside file).
- **Self-modification guard:** `ToolContext.plugin_dir` (set by the loop from the settings). `sandbox.session_allowance_ok(path, plugin_dir=)` returns False for a path in the plugin folder, the same mechanism as `.git`. `write_file` and `edit_file` pass a hook that reads it from the context. Effects: a write or edit into the folder always asks, never offers "allow for this session", and a stored allowance is not used (the loop checks `session_allowed_for` before `session.allows`). Tests: `test_plugins.py`, the guard section.
- **Config:** `plugins_enabled` (bool, default true), `disabled_plugins` (list of names, by file stem or entry point name), `plugin_dir` (a path that need not exist; a relative one is taken from the config file's folder). Flag `--no-plugins`. Bad values are `ConfigError`s that name the key.
- **Output:** `[plugins] loaded: name (N tools), ...` only when a plugin loaded. Warnings: `Warning: plugin 'x' was not loaded (Error: ...). The agent continues without it.` and `... tool 'y' was skipped: ...`. Names and error text go through `printable`.
- **Public API:** `local_agent/plugin.py` re-exports `tool`, `Risk`, `ToolContext`, `ToolCancelled` and `Preview`. The README example (one function, `count_words`) was run in a scratch folder: it loads and returns `3 words`. Its test now checks only its own plugin (`word_count`), so an unrelated broken installed entry point does not fail it. Run again in the scratchpad after the review fixes (the README file and test as written): passed.
- **Tests:** `tests/test_plugins.py` (sample files in `tests/plugin_fixtures/`, renamed from `tests/plugins/` so the name is unlikely to clash). `tests/conftest.py` has an autouse fixture `isolated_plugins`: the per-user plugin folder points at a missing temp path, the `local_agent.tools` entry points are empty, and afterwards the registry is restored and the `local_agent_plugins` stub and its `local_agent_plugins.*` modules and the `plugin_fixtures.*` modules are removed from `sys.modules`.
- **Verified:** `uv run pytest -q` gives 682 passed, 1 skipped (669 before the review fixes plus 13). `uv lock --check` exits 0. pyflakes was not run on the final change (the lint check was denied in this session).
- **Verified by the reviewer:** loading from a real installed wheel with entry points (built with `uv pip install --target` in a scratch folder, put on PYTHONPATH). This is what found S1 and S2 above, both fixed and tested.
- **Not verified:** plugins in the real `%APPDATA%` folder. A live model calling a plugin tool (the tests use the fake client). A real console Ctrl+C during a plugin tool (the plugin tools are not cancelled by the loop; see follow-ups). Ctrl+C during plugin import is tested with an injected `KeyboardInterrupt` only.
- **Follow-ups:**
  - Plugins are trusted code: they run in the agent's process with full access, and nothing sandboxes them. The folder is the trust boundary, so the README says to put only code you would run yourself there.
  - `run_command` can still write into the plugin folder (it always asks, but the question is about the command, not the folder). A stricter rule would need parsing commands, which the sandbox does not do.
  - No reload: plugins are read once at startup. A changed plugin needs a restart.
  - A long plugin tool stops early only if it checks `context.cancel`, or if Ctrl+C raises `KeyboardInterrupt` inside it. The loop does not time plugin tools out (MCP calls and run_command have a limit; plugin tools have none yet).
  - Argument types are not validated against the schema (the T02 hardening note applies to plugin tools as well).
  - An entry point whose module was imported earlier by other code registers nothing. It gets the same "registered no tools" warning as a plugin with no tools; the loader cannot tell the two apart.
  - Rollback and `close()` undo only registry key additions. Overwrites, deletions, mutated `Tool` members, monkeypatches and threads are not undone. Plugins are trusted code, so this only guards against accidents.
  - Tools registered by a package that a file plugin imports (or by a module that package imports) are attributed to that file plugin: its rollback removes them, and the loaded line counts them under it.
  - Modules a plugin imports itself, other than the loader's own (the plugin files, `local_agent_plugins.` helpers, and the entry point's top-level package), stay in `sys.modules` after `close()`. A second load in the same process therefore does not register their tools again. Removing them safely needs a rule for stdlib and third-party modules.

Failed and cancelled calls end as `failed`.

- **Server design (`frontends/server.py`):** the main thread reads stdin and answers requests. `session/prompt` runs on a worker thread. A permission wait polls the session's cancel event every 50 ms. One prompt runs per session. Each session has its own `SessionApprovals`, so "allow always" is per session, and its own workspace (`settings` copied with `workspace=cwd`; the process cwd is not changed per session). At EOF the server sets every cancel event, joins the workers (10 s at most), then closes the MCP servers and the plugins. stdin is decoded as UTF-8 (bad bytes replaced); stdout is UTF-8 with `\n` line ends, and the JSON is ASCII-only. While serving, `sys.stdout` is redirected to stderr, so a stray `print` cannot reach the protocol.
- **Start-up:** plugins, MCP servers and the model check run before the first message. Their warnings go to stderr. An Ollama that is down at start-up is a warning; the server still runs and the first prompt gets the `-32603` error.
